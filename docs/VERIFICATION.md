## 0. 前置准备

1. **启动数据库**（已建库 `tourist_service`，20 张表 + 种子）：
   ```bash
   mysql -u root -p123456 < E:\code\tourist-service\sql\init.sql
   ```
2. **启动后端**（必须 JDK 17）：
   ```bash
   cd E:\code\tourist-service\backend
   export JAVA_HOME=D:/ETjdk17
   mvn spring-boot:run          # 端口 8080
   ```
   - 确认日志出现 `Started TouristApplication`。
3. **启动前端**：
   ```bash
   cd E:\code\tourist-service\frontend
   npm install
   npm run dev                  # 端口 5173
   ```
4. 浏览器打开 `http://localhost:5173`，标题应为「武侯祠游客服务中心」，背景登录页为深红渐变、置中 logo（logo.png，点击跳 `wuhouci.net.cn`）。

> 提示：因 Session 仅当前登录用户可见，**跨角色流程需退出/登录切换账号**；通知铃右上角每 30s 轮询。

## 3. 逐角色验证（登录后应见什么 / 应测什么）

### 3.1 游客 `tourist1`
- **侧边栏**：首页、我的投诉、应急信息、景区服务(景区/线路/餐饮/演出/交通)、酒店(星级/非星级)、天气路况、修改密码。
- **我的投诉** `/complaints`：点「提交投诉」填内容→出现待审批记录；状态随时间线变化。
- **应急信息** `/emergency-info/list`：应只看到**审批通过且当天在有效期内**的信息（示例「台风预警/暴雨预警/反诈提醒」视有效期而定）。
- **景区/酒店/天气**：各列表应为只读（无新增/编辑按钮）；详情弹窗展示字段；`/weather-conditions` 显示真实武侯区天气与路况(畅通/缓慢/拥堵)。
- **酒店预订**：进入「酒店」，点某酒店→详情内列房型→点某房型「预订」→填入住/离开/人数→**总价=单价×(离开−入住+1)**→确认「预订成功」。
- **订单详情** `/my-bookings`（侧栏「酒店 → 订单详情」）：酒店名称/房型/日期/总价/状态，可**取消**。
- **注册**：登录页右下「注册账号」→ 填 用户名/手机号/邮箱/密码/请再次输入密码（两次一致才可点注册）→ 回登录页。
- **首页** `/`：显示游客欢迎语与快捷入口。

### 3.2 审批人员 `approver1`
- **侧边栏**：投诉审批、应急信息审批。
- **投诉审批** `/complaints/approval`：列出「待审批」投诉；点通过/驳回并填意见。
- **应急信息审批** `/emergency-info/approval`：列出待审批应急信息，通过/驳回。
- 证据：收到「投诉提交」通知（右上角铃）。

### 3.3 平台管理员 `platform1`
- **侧边栏**：投诉分派、投诉结案、应急信息管理、内容管理、酒店营销、数据看板、用户管理。
- **投诉分派** `/complaints/assign`：对「已通过」投诉选择处理人员（待处理下拉）→分派。
- **投诉结案** `/complaints/close`：对「已确认」投诉结案。
- **应急信息管理** `/emergency-info`：新增/编辑(修改后回退待审批)/删除。
- **内容管理** `/manage/*`：对 景区/线路/餐饮/演出/交通/星级/非星级酒店 新增/编辑/删除。
- **酒店营销** `/hotel-marketing`：录入/编辑(保存即重新发布)/删除；发布后游客收到通知（标题=酒店名，内容=营销内容）。
- **数据看板** `/dashboard`：统计卡片 + 投诉状态饼图 + 应急状态柱状图（有获批的待审批/已发布数据时图表有内容）。
- **用户管理** `/users`：按角色筛选、启用/禁用。
- 证据：投诉状态推进的若干通知。

### 3.4 投诉处理人员 `handler1`(或 `handler2`)
- **侧边栏**：待处理投诉。
- `/complaints/handler`：列出「分派给我且处理中」的投诉；点处理→填处理结果 + 上传证据附件。

### 3.5 酒店管理员 `hotel1`
- **侧边栏**：客房信息录入。
- `/hotel/rooms`：选酒店类型→选酒店→选日期→查询，列出**该酒店所有房型**（总量/当日已预定/剩余/价格）；新增/编辑房型、删除(彻底)、查看「预订明细」(预定人/房型/日期/人数/总价)。**日期只影响「当日已预定」显示**。

## 4. 核心闭环：投诉全流程（换账号依序操作）

> 这是最重要的一条验收。请在**游客**环节新建一条投诉，再从后往前换账号推进。

| 步骤 | 账号 | 操作 | 期望结果 |
|------|------|------|---------|
| 1 | `tourist1` | 我的投诉→提交投诉(填内容) | 列表出现「待审批」；右上角收到通知 |
| 2 | `approver1` | 投诉审批→通过(填意见) | 该投诉状态→「已通过」，发布标记=1 |
| 3 | `platform1` | 投诉分派→选择 `handler1` →分派 | 状态→「处理中」，处理人=投诉处理员一，处理人收到通知 |
| 4 | `handler1` | 待处理投诉→处理(填结果+可传附件) | 状态→「处理完成」，游客收到通知 |
| 5 | `tourist1` | 我的投诉→进详情→「确认」 | 状态→「已确认」 |
| 6 | `platform1` | 投诉结案→结案 | 状态→「已结案」，游客收到通知 |
| 7 | `tourist1` | 投诉详情→评分(1-5星)+提交 | 详情显示评分；状态保持已结案 |

- **详情页** `/complaints/:id`：应有 el-steps 步骤条（待审批→已通过→处理中→处理完成→已确认→已结案）、回复记录、审批时间线(节点/审批人/动作/意见)、附件。
- **驳回分支**：第 2 步改「驳回」→状态「未通过」，游客收到驳回原因。
- **状态回退**：驳回后游客**回复** → 自动回到「待审批」(重回审批列表)；处理完成后游客**回复**(未确认) → 自动回到「处理中」(重回处理列表)。
- **越权守卫**：以 `tourist1` 登录直接在地址栏进 `/complaints/approval` 等，前端路由守卫会拦截；调用写接口(如游客调审批)返回 `403 权限不足`(body)。

## 5. 应急信息闭环

| 步骤 | 账号 | 操作 | 期望结果 |
|------|------|------|---------|
| 1 | `platform1` | 应急信息管理→新增(标题/内容/生效-结束日期) | 状态「待审批」 |
| 2 | `approver1` | 应急信息审批→通过 | 状态「已发布」+ 发布时间；**所有游客收到「您收到了一条应急通知，请及时查看！」** |
| — | — | 发布时 / 驳回时 | 发布→**审批人员**收「您有一条应急通知待审批！」；驳回→**发布者**收「您发布的应急消息被驳回！」 |
| 3 | `tourist1` | 游客端应急信息列表 | **仅当** 生效日期含今天 时可见；否则不可见 |
| 4 | `platform1` | 编辑该条 | 状态回退「待审批」，需重新审批 |
| 5 | `platform1` | 删除 | 列表中移除(逻辑删除) |

## 5.1 酒店预订闭环

| 步 | 账号 | 操作 | 期望结果 |
|----|------|------|---------|
| 1 | `hotel1` | 房态录入→选「武侯祠锦华酒店」→选日期 | 列出全部房型；「商务大床房」当日已预定=基准值 |
| 2 | `tourist1` | 酒店→锦华酒店→房型「商务大床房」→预订→入住 9/10、离开 9/11、1 人 | **总价=520×2=1040** |

| 5 | `hotel1` | 房态录入切到 9/10 | 商务大床房当日已预定+1；9/12 显示原基准值 |

> 校验：`离开 < 入住` 或某日余量为 0 时应被拒绝（提示）。

## 6. 其余功能点质检

- **查询类只读**：游客在 景区/线路/餐饮/演出/交通/酒店 只读、详情弹窗正常；平台管理员在 `/manage/*` 增删改正常。
- **酒店房态**：`hotel1` 录入某酒店某日房型；同酒店同房型同日重复录入应**更新而非新增**(幂等)；游客可查。
- **天气/路况**：游客页显示真实数据（若 `AMAP_KEY` 未生效则显示 mock「多云 26℃」与「武侯祠大街/一环路南三段」示例）。
- **文件上传**：投诉处理上传证据(图片/视频等)；`/uploads/**` 可访问。
- **通知**：各角色的关键动作触发对应类型通知（`COMPLAINT_SUBMITTED/APPROVED/REJECTED/ASSIGNED/RESOLVED/CLOSED`），列表已加中文标签。
- **个人信息/修改密码**：右上角菜单→个人信息（显示用户名/手机号/邮箱）→修改密码（旧密码 `123456`）。
- **注册**：游客可自助注册（新账号为游客身份，可登录）；重复用户名被拒绝。
- **旅游线路**：列表「包含景点」列显示**景点名称**（如「武侯祠、锦里古街」），而非 ID。
- **酒店营销**：录入后出现在列表；编辑保存后内容更新并再次通知游客；删除后彻底消失。

## 8. 建议的完整验收顺序（一份顺下来）

1. 前置：启动 DB/后端/前端，见 §0；跑一次 `mvn test` 全绿。
2. 登录 `tourist1` → 检查首页/侧边栏/只读列表/天气路况/应急信息可见性。
3. 走 §4 投诉闭环（1→7 步，含详情页与通知）。
4. 另建一条投诉走「驳回」分支，验证越权守卫。
5. 走 §5 应急信息闭环（含有效期可见性、编辑回退、删除）。
6. 登录 `platform1` → 内容管理缓存/酒店营销/数据看板(图表)/用户管理。
7. 登录 `handler1/2` → 待处理投诉处理 + 上传附件。
8. 登录 `hotel1` → 房态录入(按房型新增/更新/删除、预订明细)。
9. 走 §5.1 酒店预订闭环（预订→订单→取消→房态核对）。
10. 登录页「注册账号」→ 注册→登录新账号。
9. 反向权限抽查：游客访问平台/审批路由被拦截；写接口错误角色返回 403。

> 若任一期望不符，反馈给我（说明角色+步骤+实际/期望），即可定位修复。
